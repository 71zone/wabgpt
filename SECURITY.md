# Security

## Supported use

wabgpt is designed for **one trusted owner** running it on their own machine or a private server. It is not hardened as a public or multi-tenant service. Only the current default branch is supported; there are no maintained older release lines.

## Reporting a vulnerability

Do not post exploit details in a public issue, pull request or discussion. Use the private vulnerability-reporting feature of the code host where you found this repository if it is enabled (on GitHub: the repository's Security tab, "Report a vulnerability"). If that is not available, contact a maintainer through a private channel listed on the repository's page and share details only once they reply. This repository does not publish a security email address, and none is implied.

Please include affected version or commit, impact, minimal reproduction using synthetic data, and whether the flaw needs the owner token. Never send real WhatsApp credentials, ChatGPT cookies, BrowserOS profiles or the owner token.

## What the application defends

- **Owner dashboard (`wabgpt serve`).** Everything except the login page and static assets needs authentication: owner-token login creates a bounded server-side session in an `HttpOnly`, `SameSite=Strict` cookie (`Secure` for an HTTPS `publicOrigin`). Mutations also need a per-session CSRF token and a same-origin `Origin`. Unexpected `Host` values and cross-origin reads or event streams are rejected, there is no wildcard CORS, no state-changing GET, request bodies are size-limited and login attempts are rate-limited. Private responses are `no-store`; dynamic text is rendered with `textContent`. Details: [docs/http.md](docs/http.md).
- **Owner token.** 32 random bytes from the OS CSPRNG, created with exclusive create, file mode 0600 in a 0700 directory, compared in constant time, never logged and never accepted in a URL. `wabgpt token` prints it only to an interactive terminal.
- **BrowserOS MCP.** `browserMcpUrl` must be an `http(s)` loopback URL without credentials; the application refuses anything else. The server exposes no MCP, script, file, configuration or proxy endpoint. In the default Docker stack MCP is reached only inside a shared container network namespace and is not published. In the opt-in host-browser override (`compose.host-browser.yaml`) wabgpt runs with host networking and reaches your native BrowserOS at `127.0.0.1:9010`; nothing is published and the loopback validation is unchanged. The one deliberate exception to "MCP is never published" is the managed Docker browser that the native `wabgpt` command creates during first-run setup so the native process can reach it: its MCP (9010) and noVNC viewer (6080) are published on `127.0.0.1` only, on random host ports. Before using a container it checks, from `docker inspect`, that every published binding is `127.0.0.1` and that the container is not privileged or sharing host network or PID namespaces, and it reuses only a container and volume that carry its ownership labels. The default Compose files still never publish MCP.
- **Local data.** State and credentials are written privately (directory 0700, files 0600), atomically, under a single-writer lock. Message and reply bodies are not stored. Stale locks are never removed automatically.
- **Safe-by-default delivery.** Nothing is forwarded until the owner enables a contact; uncertain submissions are never replayed; failures pause the affected route. First-run setup saves the first contact paused and enables it only after an explicit `yes` (default no) to a prompt that says their incoming text goes to ChatGPT and replies are sent automatically. It pauses forwarding while it runs, sends no ChatGPT prompt, and never signs in or solves a challenge for you.
- **Repository hygiene.** `.gitignore`, `.dockerignore` and the npm `files` allowlist exclude credentials, state, tokens, profiles, env files and backups.

## What it does not defend, and what you must do

- **Anyone who reaches noVNC (6080) or MCP (9010) controls your signed-in browser.** Neither BrowserOS service has authentication. Keep them on loopback and use an SSH tunnel or private VPN. Do not publish them, do not put them behind a public proxy and do not remove the `127.0.0.1:` prefix from `compose.yaml`; Docker's published ports bypass host firewalls such as `ufw`.
- **The managed Docker browser's ports are reachable by every local user and process.** Its loopback host ports are random but not secret, and neither service has authentication, so any local account or program that can reach `127.0.0.1` can view or drive that browser and its signed-in ChatGPT profile. Use it only on a computer you trust. The profile stays in a Docker volume (`wabgpt-neo-<id>-data`) under the same built-in-key cookie storage described below, anyone who can run `docker` can read it, and quitting wabgpt does not stop the container or delete the volume. See [docs/deployment.md](docs/deployment.md#guided-setup-with-a-managed-docker-browser) for how to find, stop or remove it.
- **Whoever holds the owner token, the data directory or the BrowserOS profile effectively is the owner.** They can act as your linked WhatsApp device or use your ChatGPT session. Back these up only to private, encrypted storage. In Docker, anyone who can run `docker` on the host can read both volumes.
- **The Docker BrowserOS image runs Chromium with `--no-sandbox` by default** (upstream default, because Docker's default seccomp profile blocks Chromium's sandbox). The container is the only isolation layer for web content. The Compose file does not relax host security to change this.
- **Container browser cookies use a built-in key** (`--password-store=basic`); files in the BrowserOS volume are readable plaintext-equivalent credentials.
- **Loopback is not authentication against other local users or processes.** On a shared host, other accounts that can reach `127.0.0.1` can reach those ports.
- **Host-browser mode widens the container's network reach.** With `network_mode: host` the `wabgpt` container shares the host's network namespace: it can connect to any service on the host's loopback (including your unauthenticated native BrowserOS MCP), and local users or processes that can reach host loopback can reach the dashboard on 8788. `deploy/config.host-browser.json` binds the dashboard to `127.0.0.1` for this reason; never set `server.host` to `0.0.0.0` or add a public bind, published MCP port, `host.docker.internal` URL or remote MCP URL. Your desktop BrowserOS profile is a separate, more sensitive credential store than the Docker one; never copy cookies between them. wabgpt does not automatically verify that ChatGPT is signed in there.
- **Contact text is sent to ChatGPT and replies are sent from your account.** Enable only contacts whose messages you are authorized to share. ChatGPT project memory and cross-project context are controlled by ChatGPT, not by wabgpt.
- **Unofficial WhatsApp client.** The Baileys dependency is a release candidate; WhatsApp may restrict accounts that use unofficial clients.
- **No built-in rate or queue limits on forwarded messages.** An enabled contact that sends faster than ChatGPT answers can build a backlog; enable only contacts you trust.
- **Dependency error text** may reach the activity log or dashboard. Treat logs as sensitive and sanitize them before sharing.
- **Supply chain.** Dependencies are pinned by `package-lock.json` and `npm ci`; BrowserOS is pinned by image digest. Updating either is a trust decision, not an automatic one.

Cloudflare or OpenAI challenges, login expiry and similar friction on `chatgpt.com` need manual action; the project does not and will not automate bypassing them.
